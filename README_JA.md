# 二次元ゲーム イベントカレンダー(anime-game-calendar)

[简体中文](README.md) | [English](README_EN.md) | [日本語](README_JA.md)

> **本プロジェクトは AI によって書かれました** — プロトタイプからフロントエンド・バックエンドのコード、クローラーカーネル、Android アプリ、そして毎日のイベント日程の確認・補録まで、すべて AI エージェントがリレー方式で担当しています。

人気の二次元ゲーム(ソシャゲ)の**公式公開 API** からイベント日程とお知らせを自動収集し、iOS 風の**月間カレンダー**(任意の日をタップしてその日のスケジュールを確認)とイベントリストに集約します。カウントダウンと進行状況バー付き。
**PC Web 版**と **Android アプリ版**を提供します。

> 対応ゲームは中国サーバー版です。データはすべて公式中国語チャンネル由来です。

## クイックスタート:リポジトリのリンクを AI エージェントに送る

本プロジェクトのインストール・設定・毎日の自動化は、メッセージ 1 つで完結です。普段使っている AI エージェントソフト(ターミナル/ファイル/ウェブ検索機能を持つものなら何でも可 — TRAE、Claude Code、Cursor など。**できれば画像を見られるマルチモーダルモデルがおすすめ**、理由は後述)で次のように送ってください:

> https://github.com/BBQMARTE/anime-game-calendar このプロジェクトをデプロイして、README の「エージェント自動化」に従って毎日のタスクを設定して

エージェントがこのドキュメントを読んで、残りをすべて行います:依存関係のインストール → サーバー起動 → 毎日の自動化作成(ウェブ検索で新イベント確認、カレンダー更新、期限切れ削除)。手動作業もコピー作業も不要です。

自分でやりたい場合は、下の[インストールと使い方](#install)に従来の手動手順があります。Android アプリは [Releases](https://github.com/BBQMARTE/anime-game-calendar/releases) から直接ダウンロードできます。

> **エージェントソフトに関する声明**:本プロジェクトは **[TRAE Work](https://www.trae.ai/) でのみテストしています**。他のエージェントソフト(Claude Code、Cursor など)はテストしていません。問題が発生した場合は TRAE Work 環境を基準にしてください。
>
> **モデル能力の推奨(重要)**:本プロジェクトは**画像を直接見られるマルチモーダル(視覚)能力を持つモデルを強く推奨**します。理由は 2 つ:
>
> 1. **画像タイプのスケジュール認識**:終末地、リバース:1999 など一部ゲームのスケジュールは画像としてのみ発表されます。WebSearch/WebFetch が返すのはテキストだけで、画像はモデルのコンテキストに入りません——**モデルがどんなに賢くても、与えられていない画像は見えません**。視覚能力のあるモデル + ブラウザ スクリーンショットで初めて画像タイプのスケジュールを読めます(下記「画像タイプスケジュール認識」参照)。
> 2. **イベントカード切り抜き**:本プロジェクトは公式の超縦長ティーザー画像を**イベントごとのカードに切り抜き**、一覧のサムネイルにできます(例:終末地の 3840px 幅の超縦長ティザー板を 19 枚以上のカードに分割)。切り抜きは「画像を見てイベントの境界を特定する」作業のため、マルチモーダル視覚能力が必須です(下記「イベントカード切り抜き」参照)。

## インストールと使い方

<a id="android"></a>

### Android アプリ版

Android 版はネイティブ WebView シェルで、2 つのモードを内蔵しています:**サーバーモード**(PC サーバーに接続し、最も完全で正確なデータを利用)と**クローラーモード**(PC 不要で、アプリ内で公式 API を直接取得)。

**直接ダウンロード:** [Releases](https://github.com/BBQMARTE/anime-game-calendar/releases) ページから APK をダウンロードし、スマホに転送してインストールしてください(不明なソースからのインストールを許可する必要があります)。

Web 版右上の**歯車ボタン**で設定:カレンダー表示のワンタップ切替、ゲームごとのカレンダー表示チェックボックス(リストのフィルターとは独立)。

**このマシンでのビルド(SDK は D: ドライブにインストール済み):**

`构建APK.bat` をダブルクリック。初回実行時にリリース署名キーが自動生成されます(`android/ycal.keystore`、パスワードは `android/keystore.properties`)。成果物は `android/app/build/outputs/apk/release/app-release.apk`。keytool がない場合は debug APK にフォールバックします。

> **`android/ycal.keystore` は必ずバックアップしてください**:キーを失うと、インストール済みアプリの上書きアップグレードができなくなります(アンインストール→再インストールのみ可)。

**他のマシンでのビルド:** Android Studio で `android/` フォルダを開き、同期後に `Build > Build APK(s)`。

Android 8.0(API 26)以上に対応。

> Android プロジェクトのページリソースは `android/app/src/main/assets/www/`(`static/` のコピー)です。
> **`static/` を編集したら `android/app/src/main/assets/www/` にコピーしてから再ビルドしてください。**

<a id="pc"></a>

### PC Web 版(手動インストール)

1. 依存関係のインストール(初回): `pip install -r requirements.txt`
2. `启动.bat` をダブルクリック(または `python app.py` を実行)
3. ブラウザで <http://127.0.0.1:5000> が自動的に開きます

- 起動時に 1 回取得し、以後 30 分ごとに自動更新。右上の更新ボタンでも更新可。
- 取得結果は `data/cache.json` にキャッシュされ、再起動後に即座に復元されます。
- システムのライト/ダークモードに自動追従します。

同じ LAN 内の他の端末(タブレット/スマホ)は `http://<PCのIP>:5000` でアクセスできます。外出先からのアクセスは[購読とリマインダー](#notify)の Tailscale 方案を参照してください。

<a id="notify"></a>

### 購読とリマインダー

| 機能 | 使い方 |
|---|---|
| **ICS カレンダー購読** | 端末の純正カレンダー / Google カレンダーで `http://<サーバー>:5000/api/calendar.ics` を購読 — 本物のイベントがすべて純正カレンダーに入ります。`?games=hsr,zzz` でゲーム、`?cats=活动,签到` でカテゴリ、`?fav=1` でお気に入りだけに絞れます(設定パネルの「購読リンク」が自動で生成・コピーし、「購読はお気に入りのみ」スイッチも用意)。`?alarm=30` を付けると開始 30 分前に端末カレンダーが通知します(設定にスイッチあり)。`ETag` 条件リクエスト対応で、更新がないときは 304 を返し再転送しません |
| **稼働状態 API** | `GET http://<サーバー>:5000/api/health` で更新時刻・24 時間超の未更新(stale)・全件/実イベント数・開催中件数・開始から 30 日超で終了不明の件数・終了日なし件数・直近 14 日の変更数・画像なし件数・各データソースの成否と最終成功時刻(`last_ok`)・直近の全体更新が失敗した理由(`last_error` / `last_error_at`)・更新中フラグを一括取得。自動化スクリプトや監視に便利 |
| **現在のビューを共有** | ゲーム / カテゴリ / タブ / 検索語で絞るとアドレスバーが `?games=hsr,zzz&tab=ongoing&q=崩铁` のように自動更新。上部バーの**共有ボタン**でワンタップコピーも可能。URL パラメータは相手のローカル記憶より優先、オフライン APK はアドレスを書き換えません。検索は「崩铁」「鸣潮」などの短縮名にも対応 |
| **PWA インストール** | タブレット/スマホのブラウザで「ホーム画面に追加」→ フルスクリーン App アイコン、オフラインでも閲覧可 |
| **イベント開始リマインダー** | `data/notify.json` に webhook(Feishu グループボット / Bark / Server酱 / PushPlus)を設定すると、`time` の時刻に今後 `lead_days+1` 日以内に開始するイベントをまとめてプッシュ(`lead_days` は 0 / 1 / 3、既定 1 = 今日・明日)。同日中に「終了間近」のセクションも付きます。送信済みマークは保存され、サーバー再起動でも重複送信しません。失敗時は最大 3 回まで再試行します |
| **外出先からアクセス** | PC とタブレットの両方に [Tailscale](https://tailscale.com) を入れて同じアカウントでログインすれば、どこからでも `http://100.x.x.x:5000` で自宅サーバーにアクセス可 |

`data/notify.json` の設定例:

```json
{
  "webhook": "https://open.feishu.cn/open-apis/bot/v2/hook/xxxxxxxx",
  "time": "08:30",
  "lead_days": 1
}
```

`lead_days` はリマインダーの先行日数です:0 = 当日、1 = 今日・明日(既定)、3 = 今後 4 日。それ以外の値は 1 として扱われます。

- **Feishu**: グループ設定 → ボット → 「カスタムボット」を追加し、webhook URL を貼る
- **Bark**(iOS アプリ): `https://api.day.app/自分のキー` を指定
- **Server酱**: `https://sctapi.ftqq.com/自分のSendKey.send`(フォーム送信で WeChat に通知)
- **PushPlus**: `https://www.pushplus.plus/send/自分のtoken`(`?token=...` 形式も可)
- 空欄なら無効。保存すれば次のサイクルで反映されます

## 対応ゲームとデータソース

| ゲーム | データソース |
|---|---|
| 崩壊:スターレイル / ゼンレスゾーンゼロ | **ゲーム内お知らせ API**(ゲーム内「お知らせ」パネルと同ソース)+ バージョン更新記事の分割 |
| アークナイツ:エンドフィールド | 公式サイトのニュースページ(詳細リンク付き)+ バージョン更新記事の分割 |
| 鳴潮 | 公式サイトの記事 API + バージョン情報からのイベント自動抽出 |
| アナンタ | Perfect World 公式ニュースページ(お知らせ/イベント/ニュース) |
| 上記 5 ゲームの公式 Bilibili アカウント | Bilibili 公開投稿 API(情報に分類) |

### 表示ロジック:本物のイベントと情報の分離

取得した内容は 2 段階に分類されます:

| 区分 | 内容 | 表示場所 |
|---|---|---|
| **イベント** | 期間限定イベント、キャラ・武器ガチャなど**開始・終了時刻を持つ**スケジュール。タイトル自動短縮、カウントダウンと進行バー付き | 開催中 / 開催予定 |
| **情報** | 修正のお知らせ、遊び方説明、ショップ更新、アンケート、公式ニュース、Bilibili 投稿 | 「すべての情報」タブのみ(直近 60 日のみ、手動登録は除外) |

上部のフィルターでゲーム別・カテゴリ別(イベント/チェックイン(签到)/キャラ・武器/お知らせ/情報)に絞り込めます。**毎日のログインボーナス・累計ログイン系イベントは自動的に「签到(チェックイン)」に分類**されるので、デイリーをやりたくない人はワンタップで除外できます。

各ゲームの**バージョン更新記事**は「新規イベント」「新規ガチャ」などのスケジュールに自動分割され、独立したイベントとして表示されます(記事自体は情報タブへ)。

## なぜデータが正確か:クローラー + AI のデュアルエンジン

最初のプロトタイプは **Kimi K3** が作り、その後は**複数の AI エージェントソフトでリレー方式により開発**(クレジットが切れるたびに次へ乗り換え)し、最終的に [TRAE Work](https://www.trae.ai/) で完成・全面テストを行いました——本プロジェクトは本当に AI が書いています。

最初のバージョンは純粋なクローラーでした:公式 API を取得し、バージョン更新記事をイベントに分割し、正規表現で期間を解析する——機能としては動きました。

しかし実際に使ってみると、取得データはエラーだらけでした。開始・終了時刻の逆転、記事本文の断片がイベントタイトルに混入、公式 API がたまに誤った内容を返してゴミデータを生成……ルールベースの解析では、こうしたエッジケースをすべて塞ぐことはできません。

そこでひらめきました:**エージェントソフトにはウェブ検索能力がある。AI に毎日公式告知を検索・確認させたらどうだろう?**

結果は素晴らしかったです。エージェントの検索結果は正確で網羅的、時刻は分単位で正確——正規表現解析とは比べものになりませんでした。カレンダー内の AI 確認済みエントリは、すべてこのチャンネルから生まれたものです。

こうしてプロジェクトは**デュアルエンジン**設計として完成しました:

| エンジン | 頻度 | 担当 |
|---|---|---|
| クローラー | 30 分ごと | 公式 API を自動取得し、鮮度を担保 |
| AI エージェント検索 | 毎日 1 回 | ウェブ検索で日程を確認・補録し、正確性を担保 |

### AI エージェント毎日の自動化プロンプト

データの正確性は、たった一つの自動化プロンプトに支えられています。[クイックスタート](#quickstart)の通りリポジトリのリンクをエージェントに送れば、このセクションを読んで**定期タスクを自分で作成**し、プロジェクトパスも自分で埋めてくれます——何もコピーする必要はありません。

プロンプト全文は以下に記載します。用途は 2 つ:① エージェントがそのまま利用するため、② 手動設定したい人が自分でコピーするため(エージェントソフトで毎日 1 回の定期タスクを作成し、例: 20:00、プロンプトを貼り付け、`<project-path>` をローカルのリポジトリパスに置き換える)。

以後エージェントは毎日自動で:サーバーの起動確認 → ウェブ検索で新イベント確認 → 画像タイプ日程の認識(ブラウザ スクリーンショット法)→ カレンダー更新 → 期限切れイベントの削除。

```text
二次元ゲームイベントカレンダーの毎日運用タスク。プロジェクトディレクトリ:<project-path>。以下の手順を厳密に実行すること。ソースコードは一切変更しないこと。

【ステップ 1:ローカルサーバーの起動確認】
http://127.0.0.1:5000/api/events にアクセスしてサーバーを確認;応答がなければプロジェクトディレクトリで python app.py をバックグラウンド起動し、10 秒待って再確認;サーバーが既に稼働中ならスキップ(稼働中のサーバーは絶対に再起動しない)。

【ステップ 2:ウェブ検索で 7 ゲームの新イベントを確認】
以下のゲームについて、過去 1〜2 日に公式発表されたイベント・ガチャの日程を検索:
- 崩壊:スターレイル(game_id: hsr)
- ゼンレスゾーンゼロ(game_id: zzz)
- アークナイツ:エンドフィールド(game_id: endfield)
- アークナイツ(game_id: arknights)
- 鳴潮(game_id: wuwa)
- アナンタ(game_id: ananta)
- リバース:1999(game_id: r1999)
重点:新バージョンの「イベント一覧/更新説明」、期間限定イベント、キャラ・武器ガチャ、毎日ログインボーナス/累計ログイン系イベントの開始・終了時刻。
確認基準:時刻は公式ソース(公式サイトのニュース、公式Bilibiliアカウント、ゲーム内告知の転載)で相互確認できたものだけを採用;時刻は北京時間で HH:MM まで正確に;確認できないものは記録しない(質より量を優先しない)。

【画像タイプ日程の認識(ブラウザ スクリーンショット法、サードパーティ API 不要)】
一部のゲーム(代表例:アークナイツ:エンドフィールド)はイベント日程を画像として発表するため、テキスト検索では見つけられない。注意:WebSearch/WebFetch はテキストしか返さず、モデルがマルチモーダルでも、コンテキストに入っていない画像は「見え」ない。解決策は、エージェントにブラウザツールで画像を直接見させること:
1. 「バージョンカレンダー/イベント一覧」画像の直リンク URL を見つける(公式Bilibili投稿や公式サイトから抽出可能)
2. ブラウザサブエージェントを派遣してその画像を開く(本プロジェクトの /api/img プロキシ経由で読み込むと直リンク防止を回避できる)、スクリーンショットを撮り、スクリーンショットに基づいてイベント名と開始・終了日を逐条書き起こす;縦長画像はスクロールして複数回撮影し全体をカバーする
3. 書き起こし結果の整合性を確認(日付がバージョン期間内、既存エントリと矛盾なし)してからステップ 3 の形式で記録し、image フィールドに日程画像の URL を記入;画像から時刻(HH:MM)が読み取れない場合は、そのゲームのアップデート慣例時刻(エンドフィールド:12:00 更新、翌日 11:59 終了)で補い、報告でその旨を明記する
4. エージェント基盤にブラウザ/スクリーンショットツールがない場合はテキスト検索にフォールバックし、認識できなかった画像 URL を報告に列挙する;画像の中身を推測することは一切許されない

【イベントカード切り抜き(視覚による位置特定、完全自動;PC Web のみ効果)】
公式ティザー/スケジュール画像は「数十個のイベントを 1 枚の超縦長画像に詰め込む」形式が多い(例:終末地の 39760px ティザー板)。一覧の各行に超縦長画像全体をサムネイル表示してもほぼ読めないため、イベント単位でカードに切り抜く:
1. マルチモーダル視覚で、長い画像を固定高さのセグメントに分割 → 各セグメントを見て、イベントのタイトル・種類・開始時刻・上下境界を確認(全体画像内でのパーセント/ピクセル範囲を出力するのがおすすめ)
2. Python/PIL で元画像(解像度はそのまま)を境界に沿ってイベントごとに 1 枚切り抜き、ファイル名はピンイン、static/img/<game_id>/ に保存
3. manual.json の該当エントリの image フィールドに相対パスを指定(例:/static/img/endfield/endfield_dafeilin.jpg);対応カードがないエントリは image を空にする
4. 1 つのイベントが複数セグメントにまたがる場合(例:「ログインカード + 報酬カード」)は 1 枚にまとめるか必要に応じて分割し、最後に静的ディレクトリが HTTP でアクセスできるか確認する
5. サードパーティ API 不要 — モデルの視覚能力 + PIL だけ。視覚能力がないモデルはこのステップをスキップし、全体画像をサムネイルとして使う

【ステップ 3:data/manual.json を更新】
1. まず既存のエントリをすべて読み込む
2. (game_id + タイトル)で重複確認し、既存のものは追加しない
3. 新規エントリを JSON 配列の末尾に追記。形式:
   {"game_id": "hsr", "id": "manual-xxxxxxxx", "title": "「イベント名」", "category": "活动", "start": "2026-08-20T10:00", "end": "2026-09-03T03:59", "link": "公式リンク", "image": "画像URL、省略可"}
   id は ICS の UID。付与を推奨し、**一度書いたら変更しない**。公式が日程変更したら start/end だけ直せば購読側はその場で更新されます。省略時は「ゲーム+タイトル」から派生。同名の復刻イベントは別 id を明示してください
   image には公式ビジュアル/日程画像の直リンクを記入(リストでは 200px サムネイル、詳細ポップアップでは 800px に圧縮して表示。シェアカードは原図を使用);なければ空文字列
   category の値:活动(イベント)/ 角色与专武(キャラ・武器ガチャ)/ 公告(お知らせ)/ 资讯(情報)
   恒常・終了時刻なしのイベントは end を空文字列に;終了時刻が現在より先のイベントのみ記録
4. 期限切れの削除:end が有効な日付で現在より前のエントリを削除;end が空文字列の恒常エントリは保持
5. 孤児画像の削除:期限切れエントリを削除した後、static/img/ 配下の全画像ファイルをスキャンし、manual.json / cache.json のいずれかのエントリの image フィールドで参照されていないファイルを削除する;参照されている・不明なものは保持し、静的ディレクトリ外のファイルには一切触れない
6. UTF-8 で保存し、JSON を有効な形式に保つ

【ステップ 4:サーバーを更新】
サーバーが稼働中なら http://127.0.0.1:5000/api/refresh に POST リクエストを送信(ヘッダー X-Requested-With: ycal)

【報告】
簡潔に報告:① サーバーの状態;② 各ゲームで新規記録したイベント;③ 削除した期限切れエントリ数;④ 新規がないゲームは「新規なし」と明記;⑤ 画像スケジュールの認識状況:どの日程画像を読み取ったか、書き起こして記録した件数、修正した既存エントリ。時刻に確信が持てないイベントは記録せず、疑わしい点を明示すること。
```

### 時間解析カーネル

イベント時刻の抽出は `timeparse.py`(Web/サーバー版)と `static/scraper.js`(Android 版、同構)が担い、実際のお知らせ文面のほとんどをカバーしています:

- **日付**: `2026年7月10日` / `2026/07/10` / `2026.07.10` / `07.10` / `7月10日` / `7/10` / 全角数字
- **時刻**: `12:00` / `12:00:00` / `12点` / `12点30分` / `12时30分`
- **期間**: `x月x日 ~ x月x日`(区切りは `~ ～ — –`、` 至 `、` 到 `、` - ` いずれも可)
  - 「イベント時間:」などのキーワードが**なくても**、隣接する 2 つの日付は期間として認識
  - `12月30日 ~ 1月5日` のような年をまたぐ期間は、終了日を自動的に翌年にロール
- **恒常**: 长期/常驻/永久/持续开放(長期・恒常・永久)などのキーワードで終了なしの恒常イベント扱い
- **イベント名**: `「」『』【】[]（）〈〉` の各括弧と `■/◆/✦` の見出し行に対応。汎用的なタイトル(「バージョンイベント」など)は除外
- **終了時刻なし**: 開始時刻のみで終了時刻が取れないイベントは、ICS 購読 / 単体カレンダーでは既定で **2 日**のウィンドウを補完。一方、月暦と「今日 / 今週」などの日付フィルタでは**開始当日のみ**表示し、架空の期間は作らない(「開催中」タブでは「終了不明」として別枠)

### 手動でイベントを追加(フォールバック)

自動取得で見落としたイベントは、2 つの方法で追加できます(上記「エージェント自動化」もこのチャンネルを利用します):

**方法 1:自分で入力** — `data/manual.json` を編集(JSON 配列、複数エントリ可)。次回更新時に自動でマージされます:

```json
[
  {
    "game_id": "ananta",
    "title": "「像素溢出」限时活动",
    "category": "活动",
    "start": "2026-08-01T10:00",
    "end": "2026-08-15T04:00",
    "link": "https://yh.wanmei.com/",
    "image": ""
  }
]
```

- `game_id` は省略可: `hsr / zzz / endfield / arknights / wuwa / ananta / r1999`
- `category` は省略可: `活动 / 签到 / 角色与专武 / 公告 / 资讯`
- 手動エントリはイベント(kind=event)として「開催中/開催予定」に直接表示され、グレーの「手動」タグが付きます。
- Android 版:アプリ内 localStorage の `ycal_manual` キーに同じ形式の JSON 配列を書き込みます。

**方法 2:AI に代行してもらう** — 公式のイベント日程画像(「アナンタ 1.2 イベントカレンダー」など)やテキストを AI アシスタントに送ると、内容を読み取って `data/manual.json` に書き込んでくれます。

- すべてのデータは公式の公開ページ/API と Bilibili の公開投稿由来です。ログインや攻略ツール的な操作は含まれません。アクセス頻度は控えめにお願いします。

- ゲームを追加するには:Web 版は `scrapers.py` の `REGISTRY` に、Android 版は `scraper.js` の `RUNNERS` に登録します。
